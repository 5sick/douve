# 보안 모델 (요약)

전체 내용과 취약점 신고 방법은 [SECURITY.md](../SECURITY.md)(영어)를 보세요.

## 신뢰 관계
- **Hub가 가장 중요합니다.** Hub를 가진 사람은 모든 서버에 라우팅을 보내고, 중계하는 통신을 보고, 고친 웹 화면을
  내줄 수 있습니다. 일부러 Hub 손 밖에 둔 것은 두 가지: Agent 업데이트(릴리스 서명 필요)와 터미널 열기(사람의
  패스키 서명을 서버가 직접 확인). Hub 서버는 비밀번호 관리자처럼 다루세요.
- **역할은 세 가지입니다.** 관리자(전부) / 운영자(허락된 서버만: 보기·터미널·그 서버 자신의 포트로 가는 서비스) /
  앱만(허락된 앱에만 로그인). 검사는 Hub가 API마다 하고(목록에 없는 API는 관리자 전용), 입구는 앱마다
  Hub에 묻는다(`/auth/verify?service=<id>`). 운영자는 허락된 서버에서 root 셸로 할 수 있는 일은 다 할 수
  있으니 터미널 권한은 SSH 권한처럼 주세요. hub.json `allowed_emails`의 사람은 항상 관리자.
- **외부 보안 감사 전입니다.** WebAuthn 검증·CBOR/COSE 파싱·세션은 이 저장소(C++)에 직접 구현했고
  단위·E2E 시험(실제 브라우저 가상 인증기)과 퍼징(Hub libFuzzer + ASan/UBSan, Agent Go 퍼징)이 있지만,
  외부 감사는 아직입니다.

## 릴리스 서명
- 릴리스의 SHA256SUMS는 minisign(Ed25519)으로 서명한다. 공식 키: `RWSAXEv+Y7MKiWfICcWzr0WkYGW6Tt92A6+Zxc5hPK1WlzaRvSgAb1ec`
- Agent는 업데이트할 때 Hub를 믿지 않는다: 공식 키(또는 `/etc/douve-agent/trusted-keys`의 키) 서명, 서명된 버전 = 지시한 버전,
  지금보다 이전 버전 아님, 내려받은 파일 = 서명된 체크섬일 때만 교체. Hub가 뚫려도 서명 없는 프로그램을 심거나 되돌릴 수 없다.
- 설치기도 서명을 확인한다. 직접 빌드한 릴리스는 `douve-sign keygen/sign` + 설치 때 `--trusted-key`.

## 터미널: 서버가 패스키를 직접 확인
- 터미널을 열 때마다 브라우저가 `douve-terminal-open:v1 · 서버 id · 계정 · 시각 · 1회용 값`에 패스키로 서명한다
  (challenge = 그 문장의 SHA-256). Hub가 확인한 뒤 그대로 넘기고, Agent가 자기 **터미널 신뢰 목록**으로 다시
  확인(origin, rpIdHash, UV, 서명, 이 서버 권한, 시각 ±2분, 1회용 값 재사용 아님)한 뒤에만 셸을 띄운다.
  다른 서버·다른 계정용 서명으로는 열리지 않는다.
- 파일 올리기·내려받기(터미널 화면, 100MB까지)도 같은 방식: 전송마다 `file-put:<계정>:<크기>:<sha256>:<경로>` /
  `file-get:<계정>:<경로>`에 서명 → Agent가 확인. 그 계정 권한으로 읽고 쓰며(`systemd-run --uid`, 권한 검사는 커널),
  올리기는 임시 파일에 받아 크기·SHA-256이 서명과 같을 때만 제자리로. 모든 전송은 감사 로그에.
- 신뢰 목록(관리자 패스키 + 운영자 패스키와 허락된 서버)은 Agent 상태 디렉터리
  (`/var/lib/douve-agent/terminal-trust.json`)에 있어 Hub가 쓸 수 없다. 처음(등록·이 버전으로 업데이트)과
  관리자 패스키가 아직 없을 때만 그대로 받고, 그다음은 목록에 있는 관리자 패스키 서명이 있어야 받는다(버전은
  늘기만). 그래서 패스키 추가·삭제, 역할 변경은 관리자가 서버 화면에서 **패스키로 승인**해야 서버에 반영된다.
- `douve-agent terminal-trust show`로 보고, `terminal-trust reset`(서버에서 root)으로 지우면 다음 목록을 처음처럼
  받는다. 파일을 읽을 수 없으면 처음부터 다시 받지 않고 터미널을 거부한다.

## 내부 길 (기기 WireGuard)
- 서비스마다 내부(등록한 기기에서만) / 외부(입구 도메인) / 둘 다. 내부 전용은 공개 입구의 표에 없어 404.
- 폰·PC = 입구의 WireGuard 피어. 키는 Hub가 만들어 설정(QR·파일)을 한 번만 보여 주고 공개키만 저장. 입구 Agent가
  WireGuard(wireguard-go)와 TCP/IP(gVisor netstack)를 프로그램 안에서 돌린다 — 커널 인터페이스·포워딩·방화벽
  변경 없음. 기기가 닿는 곳은 입구 내부 주소(10.201.0.1)의 DNS(내부 서비스 이름 → 그 주소, 나머지는 서버 DNS로),
  HTTP→HTTPS, HTTPS(입구 인증서)뿐 — 서버 네트워크에는 못 들어간다.
- 기기 주소 = 신원(WireGuard가 키별 주소만 받음) → 사용자 → 그 사람의 서비스 권한 확인 → `X-Douve-User`로 전달,
  로그인 화면 없음. 기기 삭제·역할 변경은 입구에 바로 반영. Hub가 꺼져도 저장된 표로 계속.
- 입구에 UDP 포트 하나(기본 51821). 키가 없으면 WireGuard는 아무 응답도 하지 않는다.

## 보안 점검표
- Agent가 접속할 때·6시간마다 점검: SSH 비밀번호·root 로그인(`sshd -T` 실제 값), 비밀번호를 다시 허용하는 `Match`
  블록, 자동 보안 업데이트(unattended-upgrades / dnf-automatic), 시간 동기화, 재부팅 필요, 인터넷 쪽 주소에서 열린 포트.
- "고치기"는 root로 서버를 바꾸므로 터미널처럼 보호: `douve-server-action:v1 · 서버 id · fix:<항목> · 시각 · 1회용 값`에
  패스키 서명 → Hub 확인 → Agent가 신뢰 목록으로 다시 확인한 뒤에만 실행. 다른 항목·다른 서버용 서명, 터미널 서명은
  거부. SSH는 `/etc/ssh/sshd_config.d/00-douve.conf`에 쓰고 `sshd -t`·`sshd -T`로 확인, 실패하면 되돌린다.

## 위협 모델
| 공격자 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| 인터넷의 누구나 | 입구 80/443, 공개 앱, 로그인 화면(횟수 제한) | 허용된 계정의 패스키·Google 없이 로그인, 보호 앱·Agent 접근 |
| 훔친 세션 쿠키 | 세션이 끝날 때까지 그 사람의 역할로 보기. 마지막 패스키 확인 5분 안이면 설정·서비스 변경 | 터미널 열기(서버가 확인하는 새 서명 필요), 새 패스키 확인 |
| 운영자·앱 사용자 | 허락된 서버·앱. 운영자는 터미널로 그 서버의 root | 다른 서버, 설정·사용자, 다른 서버·Hub 포트 공개 |
| **Hub 서버 root**(또는 DB 쓰기) | 라우팅 변경·앱 공개/돌리기, 입구 로그인 뒤 앱에 아무 사용자로 접속, 알림·Google 비밀값·녹화 읽기, 중계하는 터미널을 보고 **사용자가 연 세션에 입력 끼워 넣기**, 고친 화면으로 다음 패스키 터치에 다른 내용 서명받기(터치 한 번 = 서명 하나), 감사 기록 재작성(웹훅 사본으로만 발견) | 사람의 패스키 터치 없이 터미널 열기, 관리자 서명 없이 서버 신뢰 목록에 자기 키 넣기, 서명 없는 Agent 설치·되돌리기 |
| 잃어버린 기기(WireGuard 설정이 든 폰·PC) | Douve에서 그 기기를 지울 때까지 그 사람이 열 수 있는 내부 서비스 | 서버 네트워크 접근, 그 사람 권한 밖 |
| 관리 대상 서버 하나의 root | 그 서버 전부, 그 서버의 거짓 메트릭·보안 사건. 입구라면 지나가는 앱 통신과 세션 쿠키 | 다른 서버 터미널(서명이 서버 id에 묶임), 다른 서버 사칭 |
| 백업 사본 | DB 내용 읽기(알림·Google 비밀값, Agent *공개*키, 세션 토큰 해시) | 로그인, Agent 사칭(개인키·원래 토큰 없음) |

알려진 한계: 웹 화면을 Hub가 내주므로 장악된 Hub는 보여 주는 것과 다른 내용을 서명받을 수 있다(사람의 터치가
필요하고 터치마다 서버 하나에 묶인 서명 하나 — Hub에서 코드를 받지 않는 `douve ssh`가 이 틈을 닫는다).
터미널 통신은 브라우저↔서버 종단 간 암호화가 아니다(Hub가 중계). Agent가 처음 받는 신뢰 목록은 등록과 같은
TOFU. 내부 서비스 이름도 공개 인증서를 받으므로 인증서 투명성 로그에 이름이 남는다(내용은 아님). 패스키 검증 코드는 직접 구현(시험·퍼징 있음, 감사 없음).

## 원칙
1. **비밀번호 없음** — 패스키가 기본, Google 로그인은 허용 목록 한정 선택 사항. 첫 관리자는 서버에서
   출력한 일회용 초대 링크(토큰은 URL # 뒤라 로그에 남지 않음).
2. **재인증** — 설정·서비스·초대·복구 코드는 5분 안에 패스키를 다시 확인. 터미널은 열 때마다 그 터미널용 서명.
3. **최소 노출** — Hub는 127.0.0.1에서만 받고, 서버의 Agent는 들어오는 포트를 열지 않는다(밖으로 연결).
4. **fail-closed** — Hub에 닿지 않으면 로그인이 필요한 앱은 막고, 공개 앱만 저장된 표로 계속.
5. **감사** — 로그인, 재인증, 설정 변경, 터미널(화면 녹화), 노드에서의 공개를 기록. 기록은 해시 체인
   (각 행 = SHA-256(이전 행 해시 + 이 행 내용))이라 고치거나 중간을 지우면 `douve-hub audit-verify`와
   매일 자체 점검에서 걸린다(알림). 마지막 몇 행 삭제·전체 재작성은 체인만으로 못 잡으므로 웹훅 채널의
   "감사 기록도 보내기"로 서명된 사본을 밖에 둔다.
6. **세션** — 서버에 저장, DB에는 토큰의 SHA-256만. `HttpOnly; Secure; SameSite=Lax`, 같은 기기 재로그인 시 교체.
7. **입구** — 보호 앱으로 넘기기 전에 `douve_session` 쿠키와 클라이언트가 보낸 `X-Douve-User`·`Tailscale-*`
   헤더를 지우고 `X-Douve-User`를 직접 붙인다. HSTS.

## 구현 시 주의 (C++)
- WebAuthn 서버 검증은 직접 구현 → 시험 필수 (CBOR, COSE 키, 서명, rpIdHash, origin, signCount, UV).
- Google ID 토큰: JWKS 서명 검증 + `iss`/`aud`/`exp`/`email_verified`.
- 상태를 바꾸는 요청은 Hub 자신의 origin에서만 (CSRF), 화면은 CSP `script-src 'self'`.
- 보안 관련 코드는 시험 없이 머지하지 않는다.
